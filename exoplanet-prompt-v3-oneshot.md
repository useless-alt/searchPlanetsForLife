# ЗАДАЧА
Веб-приложение (SPA) «Exoplanet Habitability Explorer» для университетского хакатона. При КАЖДОМ заходе пользователя сайт сам (код в браузере) загружает данные из 6 научных API, объединяет и дедуплицирует их, заполняет пропуски физическим решателем, считает индексы обитаемости и показывает Топ-50: таблица, 3D-карта Галактики, 3D-сцена системы. Интерфейс на русском. Важны: полнота функций, научная прозрачность (происхождение каждого числа), стабильность демо, эффектный визуал.
РЕЖИМ РАБОТЫ: это ОДИН запрос, других не будет. Построй приложение целиком за один автономный прогон, без вопросов ко мне и без остановок «подтверди, что продолжать». Если что-то неоднозначно — прими решение, которое ближе всего к этому тексту, и запиши его в README.md в раздел «Принятые решения». Иди по фазам из раздела «ПОРЯДОК РАБОТЫ» последовательно; после каждой фазы запускай `tsc --noEmit`, `vitest run` и `vite build`, исправляй ошибки и только потом переходи дальше. Приложение должно собираться и запускаться после КАЖДОЙ фазы.

# ЖЁСТКИЕ ПРАВИЛА
1. Никаких выдуманных данных. Данные о планетах и звёздах приходят только из API во время работы приложения. Запрещено хардкодить списки планет, генерировать «мок-каталог», подставлять правдоподобные числа. Исключения: тестовые фикстуры внутри *.test.ts (комментарий `// TEST FIXTURE`) и физические константы (параметры Земли для калибровочной строки).
2. Запросы к API выполняет код приложения при каждом заходе (fetch в Web Worker/браузере), а не разработчик и не ИИ на этапе сборки. Файлы-снимки в public/data/snapshots/ — только аварийный слой, их создаёт скрипт, который запускает человек (см. «ТРАНСПОРТ»).
3. Имена таблиц и колонок — только из раздела «ИСТОЧНИКИ». Если колонки нет в реальной схеме — пропустить её и записать в диагностику, не выдумывать замену (см. «SCHEMA GUARD»).
4. null не равно 0. Любое отсутствующее или нефизичное значение = null. Подстановок «на глаз» нет.
5. Отказ одного источника не роняет приложение: оно работает на остальных, а при полном отсутствии сети — на резервных копиях. Пользователь всегда видит, откуда взяты данные.

Все TAP-запросы: REQUEST=doQuery, LANG=ADQL, FORMAT=json. Запрещён `select *` в любом источнике.

1) NASA Exoplanet Archive — ядро каталога планет.
 GET https://exoplanetarchive.ipac.caltech.edu/TAP/sync?query=<ADQL, пробелы как +>&format=json
 Таблица `pscomppars`: одна строка = одна планета (композит из разных публикаций, согласованность параметров не гарантируется). Ответ: массив объектов.
 Колонки: pl_name, hostname, pl_letter, discoverymethod, disc_year, pl_controv_flag, cb_flag, sy_snum, sy_pnum, pl_rade [R⊕], pl_bmasse [M⊕], pl_bmassprov, pl_dens [г/см³], pl_orbper [сут], pl_orbsmax [а.е.], pl_orbeccen, pl_insol [S⊕], pl_eqt [К], st_teff [К], st_rad [R☉], st_mass [M☉], st_lum [log10(L/L☉)], st_spectype, sy_dist [пк], sy_plx [мсд], ra [°], dec [°], hd_name, hip_name, tic_id, gaia_dr2_id, gaia_dr3_id.
 gaia_dr3_id и tic_id — строки вида «Gaia DR3 <число>», «TIC <число>». pl_bmassprov: «Mass» = истинная масса; значения про M·sin(i) без «/sin(i)» = нижняя граница (isMinMass = true).

2) Exo-MerCat (INAF) — объединённый каталог и кросс-имена.
 POST http://archives.ia2.inaf.it/vo/tap/projects/sync (form-urlencoded). Таблица `exomercat.exomercat`. Адрес HTTP: со страницы по HTTPS — только через proxy.
 Кандидаты колонок (берутся только существующие в схеме): exomercat_name (в старой версии `name`), nasa_name, eu_name, host, letter, main_id, main_id_ra, main_id_dec (СТРОКИ в градусах -> parseFloat), binary, mass [M_Jup], mass_min, mass_max, mass_url (происхождение лучшей массы: масса или минимальная), msini [M_Jup], p [сут], a [а.е.], e, i [°], r [R_Jup], discovery_year, discovery_method, status.
 Роль: перекрёстные имена (nasa_name <-> eu_name <-> exomercat_name) для дедупликации и планеты, которых нет в NASA.

3) Exoplanet.eu (LESIA, Парижская обсерватория).
 POST http://voparis-tap-planeto.obspm.fr/tap/sync (HTTP -> через proxy на HTTPS-странице). Таблица `exoplanet.epn_core`. Формат ответа DaCHS: парсить толерантно (см. «ПАРСЕР»).
 Кандидаты колонок: target_name (если пусто — granule_uid; это имя планеты), alt_target_name (алиасы через запятую), star_name, ra, dec, mass [M_Jup], mass_sin_i [M_Jup], radius [R_Jup], semi_major_axis [а.е.], eccentricity, orbital_period | period [сут] (взять первую существующую), star_mass [M☉], star_radius [R☉], star_teff [К], star_age [Гг], star_distance | distance [пк], star_spec_type | star_sp_type, discovered [год], detection_type, publication_status.

4) ESA Gaia DR3 — параметры звёзд.
 POST https://gea.esac.esa.int/tap-server/tap/sync. Запрос по source_id, число из NASA gaia_dr3_id (после «Gaia DR3 »), порциями ≤ 400 id:
 SELECT ap.source_id, ap.teff_gspphot, ap.radius_gspphot, ap.radius_flame, ap.lum_flame, ap.mass_flame, gs.parallax, gs.parallax_over_error FROM gaiadr3.astrophysical_parameters AS ap JOIN gaiadr3.gaia_source AS gs ON gs.source_id = ap.source_id WHERE ap.source_id IN (…)
 Единицы: teff К, радиус R☉, светимость L☉ (линейная), масса M☉, параллакс мсд.
 Анонимный sync-запрос режет выдачу примерно на 2000 строк БЕЗ ошибки: порции ≤ 400 и проверка «строк <= id». Если JOIN вернул ошибку — fallback: два отдельных запроса (astrophysical_parameters и gaia_source) и слияние по source_id. Параллелизм ≤ 2; на 429 — ретрай по Retry-After.

5) CDS SIMBAD — кросс-идентификация, спектральный тип, параллакс.
 POST https://simbad.cfa.harvard.edu/simbad/sim-tap/sync (основное зеркало). Запасные, по порядку: https://simbad.cds.unistra.fr/simbad/sim-tap/sync, https://simbad.u-strasbg.fr/simbad/sim-tap/sync. Параметры формы: query, format=json, lang=ADQL, request=doQuery. Таблицы БЕЗ префикса схемы: basic(oid, main_id, ra, dec, sp_type, plx_value), ident(id, oidref).
 SELECT i.id AS query_id, b.main_id, b.ra, b.dec, b.sp_type, b.plx_value FROM ident AS i JOIN basic AS b ON b.oid = i.oidref WHERE i.id IN ('Gaia DR3 …', …)  -- порции ≤ 300
 Для поиска использовать ТОЧНУЮ строку из NASA gaia_dr3_id («Gaia DR3 N»), для звёзд без неё — tic_id («TIC N»). Нормализацию имён не придумывать.

6) Exo.MAST (STScI) — ТОЛЬКО ЛЕНИВО, при открытии карточки или перелёте к планете, никогда при старте и не массово.
 Базa https://exo.mast.stsci.edu/api/v0.1
 GET /exoplanets/identifiers/?name=<имя> -> canonicalName, planetNames, имя звезды, ra/dec.
 GET /exoplanets/<canonicalName>/properties/ -> массив словарей (первый — композит NASA, второй — Exoplanets.org); читать по whitelist ключей с суффиксом `_unit` (например Mp/Mp_unit, Ms/Ms_unit), незнакомые ключи игнорировать.
 GET /spectra/<planet>/filelist и GET /spectra/<planet>/file/<filename>/ (text/plain; строки на «#» — комментарии; числовые колонки: длина волны, значение, ошибка). Для большинства планет спектров нет — это нормальный случай, UI показывает «спектров нет».

# SCHEMA GUARD (защита от выдуманных колонок)
Перед основным запросом каждого TAP-источника: `SELECT column_name FROM TAP_SCHEMA.columns WHERE table_name = '<таблица>'` (NASA: pscomppars; Exo-MerCat: exomercat.exomercat; Exoplanet.eu: exoplanet.epn_core; Gaia: gaiadr3.astrophysical_parameters и gaiadr3.gaia_source; SIMBAD: basic, ident). SELECT строится только из пересечения «желаемые ∩ существующие» (сравнение без учёта регистра). Результат схемы кэшируется в IndexedDB на 24 ч. Если нет обязательной колонки источника (имя планеты для каталогов, source_id для Gaia) — источник получает статус «схема изменилась» и использует резерв. Список отсутствующих желаемых колонок показывается в панели диагностики.

# ПАРСЕР ОТВЕТОВ
parseTapResponse(json): массив -> массив объектов; объект с `data` и одним из `metadata`/`columns`/`fields` -> собрать объекты по именам колонок (регистр не важен); иначе исключение UnknownFormat. При UnknownFormat один раз повторить тот же запрос с FORMAT=csv и разобрать papaparse (header: true). Тело ответа не JSON (VOTable-ошибка, HTML) -> ошибка с текстом первых 200 символов. Все числа проходят через num(v): null, '', 'NaN', не конечные -> null.

# ТРАНСПОРТ И УСТОЙЧИВОСТЬ
fetchWithPolicy(source, request):
 1. Страница открыта по HTTPS, а URL по HTTP (Exo-MerCat, Exoplanet.eu) -> сразу через proxy: браузер блокирует такой запрос независимо от CORS.
 2. Иначе прямой fetch. При TypeError (CORS/сеть/DNS) — один повтор через proxy и пометка `useProxy = true` для источника до конца сессии.
 3. Ретраи на 429/502/503/504: до 3 попыток, пауза 1.5 с · 2^n ± случайные 20%, учитывать Retry-After.
 4. Таймауты (AbortController): NASA 60 с, Gaia 90 с, остальные 45 с.
 5. Параллелизм: ≤ 2 на Gaia, ≤ 3 на остальные, ≤ 6 всего.
Proxy `api/proxy.ts` (Vercel Edge Runtime, стриминг ответа, чтобы не упереться в лимит тела ответа обычной serverless-функции):
 - GET/POST `?u=<encodeURIComponent(url)>`, тело POST передаётся как есть;
 - allowlist ТОЧНЫХ хостов: exoplanetarchive.ipac.caltech.edu, gea.esac.esa.int, voparis-tap-planeto.obspm.fr, archives.ia2.inaf.it, simbad.cfa.harvard.edu, simbad.cds.unistra.fr, simbad.u-strasbg.fr, exo.mast.stsci.edu; любой другой хост -> 403 (защита от SSRF);
 - без cookie, `Access-Control-Allow-Origin: *`; для GET `Cache-Control: public, s-maxage=21600, stale-while-revalidate=86400`.
 В dev-режиме прямые запросы; если CORS мешает — `vercel dev`.
Четыре уровня данных для каждого источника (в таком порядке): LIVE -> IDB-копия (последний успешный ответ) -> встроенный снимок `public/data/snapshots/<source>.json` (если файл существует) -> источник пропущен. Уровень всегда показывается в UI. Скрипт `scripts/make-snapshots.mjs` (Node 18+) использует те же модули src/lib/sources с прямым транспортом, пишет снимки с метаданными; запускает его человек перед демо.
Старт без ожидания: если в IDB есть копия, приложение сразу показывает расчёт по ней со статусом «обновляется…», а live-загрузка идёт параллельно (stale-while-revalidate); по завершении данные заменяются и пересчитываются.

# ПОРЯДОК ЗАГРУЗКИ (progressive, в Worker)
Этап A: NASA. Этап B (параллельно): Exo-MerCat, Exoplanet.eu. Этап C: Gaia и SIMBAD по идентификаторам из NASA. После каждого этапа — merge, решатель, `postMessage` в UI (не чаще раза в 400 мс). # РЕЗЕРВНЫЕ КОПИИ (IndexedDB через idb)
Ключи `backups/<source>/latest` и `backups/<source>/<YYYYMMDD_HHMMSS>`. Значение: {meta: {source, endpoint, fetchedAt, recordCount, sha256, schemaVersion}, payload}. Перед записью проверка: валидная структура, обязательные поля, recordCount > 0 и не меньше 50% от предыдущей latest (защита от обрезанного ответа). Запись новой версии и обновление latest — в одной транзакции; старая версия не удаляется до успеха записи. Хранить последние 5 версий на источник (константа в config.ts). sha256 — crypto.subtle. В UI: откат к выбранной версии, экспорт JSON резервной копии.
Статусы источника: «Обновлено» | «Используется резервная копия от <дата/время>» | «Встроенный снимок от <дата>» | «Ошибка: данных нет — источник пропущен». При любом статусе, кроме «Обновлено», — заметный баннер: «Не удалось обновить <источник>. Используются резервные данные от <дата/время>». Журнал ошибок (последние 50): время, источник, endpoint, причина, какой уровень использован.

# МОДЕЛЬ ДАННЫХ, ДЕДУПЛИКАЦИЯ И СЛИЯНИЕ (Worker)
PlanetEntity {id, names[], sources[], fields: Record<FieldKey, Candidate[]>, status: 'confirmed'|'candidate'|'unknown', dedupWarnings[]}; Candidate {value, source, fetchedAt, tier: 'live'|'cache'|'snapshot'}. Поля: planet — rade, masse(+isMinMass), orbper, orbsmax, ecc, insol; star — teff, rad, mass, lum, spectype, dist; coords — ra, dec.
Приведение единиц: M_Jup × 317.83 -> M⊕; R_Jup × 11.209 -> R⊕; L = 10^st_lum (NASA); расстояние из параллакса: 1000/plx пк, только если plx > 0 (для Gaia ещё parallax_over_error >= 5) и только как fallback для sy_dist.
Ключи: normName(s) = NFKD, нижний регистр, удалить всё кроме букв и цифр («Kepler-442 b», «Kepler-442b», «kepler 442 b» -> `kepler442b`). Алиасы Exoplanet.eu делятся по «,» «;» «|». hostKey = normName(имя звезды без хвоста-буквы планеты); letter = последняя одиночная строчная буква b..z.
Правила сопоставления (первое сработавшее побеждает; порядок обработки: NASA -> Exo-MerCat -> Exoplanet.eu):
 S0 явные связи Exo-MerCat: nasa_name и eu_name (окончательно);
 S1 normName имени или любого алиаса есть в индексе;
 S2 hostKey + letter;
 S3 координаты: угловое расстояние <= 15″ (допуск на собственное движение и эпохи) И (letter совпала ИЛИ |ΔP|/P <= 1.5% ИЛИ |Δa|/a <= 3%); индекс — сетка 0.01° по RA/Dec с учётом cos(dec), сравнивать только соседние ячейки (не O(n²));
 S4 иначе — новая сущность.
Если S3 даёт несколько кандидатов — взять ближайшего по периоду; если неоднозначно — НЕ склеивать (лучше дубль, чем ложное слияние) и записать в dedupWarnings. Звёздные источники (Gaia, SIMBAD) присоединяются к сущностям по gaia_dr3_id и tic_id из NASA.
Статус сущности: 'confirmed' — есть в NASA pscomppars либо источник явно пишет Confirmed; 'candidate' — источник явно пишет Candidate/False Positive; иначе 'unknown'. Все записи грузятся и учитываются в «Всего в базе»; в рейтинге по умолчанию скрыты только явные кандидаты (переключатель «Показывать кандидатов»).
Разрешение значения поля:
 - Приоритет по типу поля (config.ts, редактируемый): звёздные teff/rad/mass/lum: Gaia > NASA > Exoplanet.eu > Exo.MAST; параметры планеты: NASA > Exo.MAST > Exo-MerCat > Exoplanet.eu; расстояние: NASA > Exoplanet.eu > параллакс (Gaia/SIMBAD); спектральный тип: SIMBAD > NASA > Exoplanet.eu; координаты: NASA > SIMBAD > Gaia > Exoplanet.eu > Exo-MerCat.
 - Один кандидат — берётся он. Несколько — берётся самый приоритетный, затем проверка консенсуса: если он отличается от медианы остальных больше допуска (относительные: st_teff 8%, st_rad 25%, st_lum 40%, st_mass 25%, pl_rade 20%, pl_bmasse 40%, orbper 1%, orbsmax 5%, dist 10%; эксцентриситет абсолютно 0.1) — выбирается кандидат, ближайший к медиане всех. При двух кандидатах с расхождением — остаётся приоритетный, но ставится conflict = true.
 - Истинная масса (Mass) всегда важнее M·sin(i) независимо от приоритета.
 - Для каждого поля хранится: значение, источник, дата, уровень (live/cache/snapshot), conflict и альтернативы (для аудита в карточке).
 Происхождение 'measured' = значение из каталога (с указанием источника); 'physics' и 'model' — как в решателе.

# ФИЗИЧЕСКИЙ РЕШАТЕЛЬ ПРОПУСКОВ
Каждое производное значение хранится как {value: number|null, origin: 'measured'|'physics'|'model'|null}. Происхождение производного = худшее из входных (model > physics > measured), но не лучше 'physics'. Порядок строго такой:
Уровень А (физика, без штрафа Q_data):
 1. L [L☉]: есть из каталога (Gaia lum_flame или 10^st_lum) -> measured; иначе при st_rad и st_teff: L = st_rad^2 · (st_teff/5772)^4 (physics).
 2. Если нет одной из пары a/P и известна st_mass: a = (st_mass · (P/365.25)^2)^(1/3); P = 365.25 · sqrt(a^3 / st_mass).
 3. e: null -> e = 0 и флаг eAssumed = true.
 4. S [S⊕]: каталожное pl_insol (measured), иначе L / (a^2 · sqrt(1 − e^2)) (physics).
 5. T_eq [К] = 255 · S^0.25 ВСЕГДА (physics). pl_eqt не использовать (у NASA другое альбедо; смешение с +33 К даёт ошибку), показывать только справочно в карточке.
 6. T_s = T_eq + 33.
 7. rho = 5.51 · M / R^3; v_e = sqrt(M / R) (земные единицы).
Уровень Б (Чен — Киппинг 2017, origin 'model', штраф Q_data −0.10):
 - известен только R: R < 1.23 -> M = R^3.58; 1.23 <= R <= 12 -> M = 1.43 · R^1.70; R > 12 -> M остаётся null.
 - известна только M: M < 2.04 -> R = M^0.279; 2.04 <= M < 132 -> R = 0.81 · M^0.588; M >= 132 -> R остаётся null.
Уровень В (адаптивное исключение): n = 4 субиндекса: ESI_R, ESI_rho, ESI_ve, F_HZ. Невычислимый субиндекс исключается, k = число доступных, корень степени 1/k. Порог k >= 3. При k < 3: insufficient_data = true, индекс 0.00, запись остаётся в массиве и уходит за пределы Топ-50.

# ИНДЕКСЫ
ESI_i = (1 − |x − x0| / (x + x0)) ^ w. (x0, w): R (1.0; 0.57), rho (5.51; 1.07), v_e (1.0; 0.70), S (1.0; 1.07), T_s (288; 5.58).
ESI_interior = (ESI_R · ESI_rho · ESI_ve)^(1/3).
Зона обитаемости (Коппарапу): T* = T − 5780; S_eff = S_sun + a·T* + b·T*^2 + c·T*^3 + d·T*^4. Коэффициенты (S_sun, a, b, c, d):
 cons_in (runaway greenhouse): 1.107, 1.332e-4, 1.580e-8, -8.308e-12, -1.931e-15
 cons_out (maximum greenhouse): 0.356, 6.171e-5, 1.698e-9, -3.198e-12, -5.575e-16
 opt_in (recent Venus): 1.776, 2.136e-4, 2.533e-8, -1.332e-11, -3.097e-15
 opt_out (early Mars): 0.320, 5.547e-5, 1.526e-9, -2.874e-12, -5.011e-16
Переключатель «Консервативная / Оптимистичная» выбирает пару in/out.
d_in = sqrt(L / S_eff_in); d_out = sqrt(L / S_eff_out); d_eff = a · (1 − e^2)^0.25; HZD = (2·d_eff − d_out − d_in) / (d_out − d_in); F_HZ = max(0, 1 − HZD^2).
Температура T для S_eff: если 2600 <= st_teff <= 7200 К — как есть; если 2300 <= st_teff < 2600 или 7200 < st_teff <= 7600 — полином считается в ближайшей границе диапазона, ставится флаг hzExtrapolated и бейдж «ЗО: экстраполяция» (так остаются планеты у TRAPPIST-1); вне [2300, 7600] или при d_out <= d_in -> F_HZ = null (субиндекс исключается).
Штрафы: P_rocky(R) = 1/(1 + exp(5·(R − 1.65))); P_ecc(e) = 1 − e^2; P_star = 0.85 при st_teff < 3900, иначе 1.00.
Q_data: старт 1.00; −0.10 если M или R получены на Уровне Б; −0.05 если eAssumed (кроме P < 10 сут); −0.05 за каждый субиндекс, исключённый на Уровне В (только в режиме «Адаптивный»); итог max(0.75, Q_data). Бейдж: >= 0.95 «Высокая», 0.85–0.95 «Средняя», < 0.85 «Оценочная» (пороги в config.ts). Чекбокс выключает свой множитель (подставляется 1).

# РЕЖИМЫ (4 пресета)
1. «Адаптивный»: geomean(доступные из ESI_R, ESI_rho, ESI_ve, F_HZ) · P_rocky · P_ecc · P_star · Q_data (k >= 3). При полных данных НЕ равен RHI — это осознанно.
2. «RHI»: sqrt(ESI_interior · F_HZ) · P_rocky · P_ecc · P_star · Q_data; считается только если все 4 субиндекса доступны, иначе планета в этом режиме не ранжируется.
3. «Упрощённый ESI (R, S)»: sqrt(ESI_S · ESI_R), без штрафов и Q_data. Подпись в UI именно такая (это не PHL-ESI).
4. «Строгий научный»: sqrt(ESI4 · F_HZ), ESI4 = (ESI_R·ESI_rho·ESI_ve·ESI_T)^(1/4), без штрафов и Q_data; только планеты, у которых R, M (истинная, isMinMass = false), e, a или P, st_teff, st_mass, L или st_rad имеют origin 'measured' (rho, v_e, S, T_eq — производные от них допустимы).
Чекбоксы штрафов и Q_data активны только в режимах 1 и 2 (в остальных disabled с подсказкой). Переключатель границ влияет на режимы 1, 2, 4. Ползунок Q_data (75–100%) фильтрует выдачу во всех режимах независимо от чекбокса.
Ранжирование: индекс по убыванию, при равенстве Q_data по убыванию, затем имя. Топ-50 строится ПОСЛЕ фильтров. Дельта: classicRank − currentRank, где classicRank — глобальный ранг по режиму 3 среди всех планет, у которых он считается (положительное = поднялась, формат [+8]/[-12]); в режиме 3 колонка показывает «—».
Счётчик: «Всего в базе: N | Рассчитано: N1 | В строго измеренных: N2» (N — уникальные сущности после дедупликации, N1 — ранжируемые в текущем режиме с учётом фильтров, N2 — удовлетворяют критерию режима 4).
Пересчёт мгновенный (< 100 мс), без кнопок «Применить»; debounce 150 мс для ползунков; кнопки «Сбросить настройки» и «Сбросить фильтры».
Калибровка: строка «Земля (эталон)» вне Топ-50, считается из физических констант тем же кодом. Известное свойство формулы F_HZ = 1 − HZD²: Земля у внутреннего края зоны получает F_HZ ≈ 0.25 (консервативная) и RHI ≈ 0.48, а TRAPPIST-1 e около 0.62. Это НЕ ошибка реализации, формулу не «исправлять»; описать в разделе «Методика».

# ФИЛЬТРЫ
Спектральный класс (мультивыбор; из st_spectype, иначе по st_teff: M <3900, K 3900–5200, G 5200–6000, F 6000–7500, A 7500–10000, B 10000–30000, O >=30000), диапазон R, диапазон T_s, диапазон e, переключатель «Показывать кандидатов». Планеты с null в фильтруемом поле при активном фильтре по этому полю исключаются.

Левая часть — таблица Топ-50 (TanStack Table, сортировка: ранг, индекс, Q_data, R, M, T_s, расстояние). Колонки: ранг и сдвиг, индекс (0–100%), бейдж Q_data (tooltip), R, M (префикс «~» если origin ≠ measured), e, спектральный класс, расстояние (пк), кнопка «Приблизить». Правая часть — 3D-карта. # 3D-КАРТА (Фаза 4)
Координаты один раз после слияния: x = r·cos(dec)·cos(ra), y = r·cos(dec)·sin(ra), z = r·sin(dec), r = merged sy_dist (пк), экваториальная J2000, Земля в (0,0,0). Планеты без ra/dec/dist на карту не попадают (счётчик «без координат: N»). Радиальное сжатие r' = K·log10(1 + r) с сохранением направления (без него Топ-50 сливается в точку; K подобрать так, чтобы 3000 пк помещались в кадр).
Фон: все планеты — один THREE.Points (BufferGeometry), приглушённые. Топ-50: пул ровно из 50 меток (прицел + подпись + невидимая зона hover/raycast), перемещаются на новые координаты при пересчёте; лишние скрываются (visible=false, raycast отключён). Топ-50 светятся изумрудным (#10b981), выбывшие тускнеют. Закреплённая планета вне Топ-50 остаётся видимой отдельной меткой «выбранная». Управление: OrbitControls, «Обзор / Сбросить камеру», плавный перелёт (lerp камеры).

# 3D-СЦЕНА СИСТЕМЫ (Фаза 5)
Процедурные шейдеры, без внешних текстур и моделей. Звезда: цвет по st_teff (аппроксимация blackbody -> sRGB), размер по st_rad, свет — PointLight. Планета: тип по правилам (rocky = R < 1.6): rocky и T_s < 230 -> ледяной; 230–330 -> землеподобный (океан + облака); 330–450 -> пустынный; > 450 -> лавовый; 1.6 <= R < 4 -> мини-нептун; 4 <= R < 8 -> ледяной гигант; R >= 8 -> газовый гигант. Вращение, дрейф облаков, синхронное вращение при P < 10 сут или st_teff < 3900. Орбита (эллипс с e), зона обитаемости (кольцо d_in–d_out). Масштаб: «Обзорный» (по умолчанию, расстояние d сжимается логарифмически, звезда и планета в одном кадре) и «1:1» (реальные пропорции, допускается видеть только планету или только звезду); переключение сохраняет выбор и плавно двигает камеру. Тумблеры «Орбита» и «Зона обитаемости». Бейдж в углу «Реконструкция по расчётной модели» при Уровне Б.
Заглушка при insufficient_data или отсутствии R/T_s: планета — тёмно-серая сфера без рельефа и атмосферы; звезда — по реальным параметрам, если st_teff/st_rad известны, иначе тоже серая; вокруг неопределённого объекта облако пыли (Points); над планетой «?» и подпись «недостаточно данных для отрисовки», при hover — список недостающих полей. Обязателен dispose() геометрий, материалов, текстур при смене планеты и размонтировании.
Exo.MAST (лениво, не блокируя анимацию): identifiers -> properties -> spectra/filelist; если есть файлы спектров — график Recharts (длина волны/значение с ошибкой); при ошибке или CORS — уведомление и прежние данные. Автоматического запроса при старте нет.
