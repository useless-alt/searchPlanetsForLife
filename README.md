# Exoplanet Habitability Explorer

Одностраничное приложение для поиска и сравнения потенциально обитаемых экзопланет. Оно
загружает научные каталоги из API при каждом заходе, сводит их в одну сущность на планету,
считает индексы обитаемости, строит Топ-50 и показывает данные в таблице, на 3D-карте Галактики
и в 3D-сцене системы. Интерфейс — на русском языке.

Ключевые принципы:

- **только реальные данные** — никаких мок-каталогов и правдоподобных подстановок;
- **`null` ≠ 0** — отсутствующее или нефизичное значение остаётся `null`;
- **происхождение каждого числа** — «Измерено» / «Физика» / «Модель», источник и дата;
- **деградация без падения** — LIVE → IndexedDB → встроенный снимок → пропуск источника;
- **прозрачная методика** — формулы, штрафы и ограничения описаны в приложении и ниже.

## Возможности

- Четыре режима ранжирования: «Адаптивный», «RHI», «Упрощённый ESI (R, S)», «Строгий научный».
- Топ-50 после фильтров; сортировка, дельта к «Упрощённому ESI», бейдж Q_data, экспорт CSV.
- Фильтры по спектральному классу, радиусу, T_s, эксцентриситету и кандидатам; состояние в URL.
- Карточка планеты: параметры с происхождением, расхождения источников, декомпозиция балла,
  радар-сравнение с Землёй, ленивая загрузка Exo.MAST и график спектра (если данные есть).
- 3D-карта Галактики в экваториальных координатах J2000 и 3D-сцена системы с процедурными
  шейдерами, зоной обитаемости, масштабами «Обзорный» / «1:1» и заглушкой при нехватке данных.
- Панель источников: уровень, время, число записей, диагностика схемы, журнал ошибок,
  откат к одной из пяти резервных версий и экспорт JSON.
- Калибровочная строка «Земля (эталон)» вне Топ-50 — считается тем же кодом из констант.

## Стек

Vite 5, React 18, TypeScript strict, Tailwind CSS, компоненты в стиле shadcn/ui, lucide-react,
Zustand, TanStack Table, three.js + @react-three/fiber + @react-three/drei, zod, idb,
Recharts, papaparse (только CSV-fallback), vitest, @supabase/supabase-js (только на сервере).
Тяжёлый пайплайн выполняется в module Web Worker; ранжирование и фильтры — на главном потоке
через `useMemo`.

## Источники и уровни данных

| Источник | Таблица / API | Роль |
|---|---|---|
| NASA Exoplanet Archive | `pscomppars` | ядро каталога: планеты, звёзды, координаты |
| Exo-MerCat (INAF) | `exomercat.exomercat` | кросс-имена, кандидаты, объединённый каталог |
| Exoplanet.eu (LESIA) | `exoplanet.epn_core` | независимые значения и консенсус |
| ESA Gaia DR3 | `gaiadr3.astrophysical_parameters` | T_eff, радиус, светимость, масса звезды |
| CDS SIMBAD | `basic` | спектральный тип, координаты, параллакс |
| Exo.MAST (STScI) | REST API v0.1 | свойства, спектры и identifiers по запросу |

Все TAP-запросы используют `REQUEST=doQuery`, `LANG=ADQL`, `FORMAT=json` и **явный список
колонок**; `select *` запрещён. Перед запросом выполняется SCHEMA GUARD: приложение читает
`TAP_SCHEMA.columns` (кэш 24 ч) и оставляет только реально существующие колонки, а отсутствующие
пишет в диагностику. Ответ разбирается как JSON-массив, форма `{metadata|columns|fields, data}`
или CSV-fallback (papaparse). Числа приводятся через `num()`: пустая строка, `NaN`, `Infinity` и
нефизичные значения дают `null`, а не ноль.

Для каждого источника действуют пять уровней:

1. **LIVE** — свежий ответ API; записывается в IndexedDB.
2. **IndexedDB** — последняя успешная версия. При старте она показывается сразу, а LIVE-загрузка
   идёт параллельно (stale-while-revalidate).
3. **Supabase (Postgres)** — последняя выгрузка источника, загруженная в базу. Используется,
   если LIVE недоступен и в IndexedDB пусто.
4. **Встроенный снимок** — `frontend/public/data/snapshots/<source>.json`, если LIVE, IDB и
   Supabase недоступны.
5. **Пропуск** — данных нет; источник не роняет приложение.

Уровень всегда виден в панели источников и в строке состояния. Gaia и SIMBAD без подходящих
идентификаторов получают статус «Пропущен — нет идентификаторов», а не ошибку. Exo.MAST не
участвует в стартовых уровнях и не имеет снимка.

Транспорт: HTTP-источники (Exo-MerCat, Exoplanet.eu) сразу идут через прокси, потому что
браузер блокирует HTTP-запросы со страницы HTTPS. Для HTTPS-источников сначала выполняется
прямой `fetch`, при CORS/сетевой ошибке — один повтор через прокси и пометка источника. Есть
ретраи на 429/502/503/504 (до 3 попыток, экспоненциальная пауза с джиттером, учёт
`Retry-After`), таймауты и ограничения параллелизма. Edge-прокси принимает только хосты из
allowlist и не пропускает cookie.

## Методика

### Решатель

Значения проходят три уровня. Происхождение производного значения не лучше худшего из входных,
но и не лучше `physics`: `model` > `physics` > `measured`.

**Уровень А — физика, без штрафа Q_data:**

1. Светимость: каталожная (`Gaia lum_flame` или `10^st_lum`, `measured`), иначе
   `L = R_*² · (T_eff / 5772)⁴` (`physics`).
2. Если известна одна из пары `a`/`P` и масса звезды:
   `a = (M_* · (P / 365.25)²)^(1/3)` или `P = 365.25 · sqrt(a³ / M_*)`.
3. Эксцентриситет: `null → 0` с флагом `eAssumed = true`.
4. Поток: каталожный `pl_insol` (`measured`), иначе
   `S = L / (a² · sqrt(1 − e²))` (`physics`).
5. `T_eq = 255 · S^0.25` — всегда `physics`. `pl_eqt` не используется в расчёте и показывается
   только справочно в карточке (у NASA другое альбедо).
6. `T_s = T_eq + 33`.
7. `ρ = 5.51 · M / R³`; `v_e = sqrt(M / R)` в земных единицах.

**Уровень Б — Чен—Киппинг 2017, `model`, Q_data −0.10:**

| Известно | Диапазон | Формула |
|---|---|---|
| только `R` | `R < 1.23` | `M = R^3.58` |
| только `R` | `1.23 ≤ R ≤ 12` | `M = 1.43 · R^1.70` |
| только `R` | `R > 12` | `M = null` |
| только `M` | `M < 2.04` | `R = M^0.279` |
| только `M` | `2.04 ≤ M < 132` | `R = 0.81 · M^0.588` |
| только `M` | `M ≥ 132` | `R = null` |

**Уровень В — адаптивное исключение:** четыре субиндекса `ESI_R`, `ESI_ρ`, `ESI_v`, `F_HZ`.
Невычислимый субиндекс исключается, `k` — число доступных, корень степени `1/k`. Порог `k ≥ 3`.
При `k < 3` ставится `insufficientData = true`, индекс в «Адаптивном» равен `0.00`, запись
остаётся в массиве, но не попадает в ранжирование и Топ-50. В «RHI» такая планета не
ранжируется (`null`), потому что режим требует все четыре субиндекса.

### Индексы

```text
ESI_i = (1 − |x − x0| / (x + x0))^w
```

| Величина | `x0` | `w` |
|---|---:|---:|
| Радиус `R` | 1.0 | 0.57 |
| Плотность `ρ` | 5.51 | 1.07 |
| Скорость убегания `v_e` | 1.0 | 0.70 |
| Поток `S` | 1.0 | 1.07 |
| Температура `T_s` | 288 | 5.58 |

```text
ESI_interior = (ESI_R · ESI_ρ · ESI_v)^(1/3)
ESI4         = (ESI_R · ESI_ρ · ESI_v · ESI_T)^(1/4)
```

### Зона обитаемости

Используется модель Коппарапу. `T* = T_eff − 5780`,

```text
S_eff = S_sun + a·T* + b·T*² + c·T*³ + d·T*⁴
d_in  = sqrt(L / S_in)
d_out = sqrt(L / S_out)
d_eff = a · (1 − e²)^(1/4)
HZD   = (2·d_eff − d_out − d_in) / (d_out − d_in)
F_HZ  = max(0, 1 − HZD²)
```

Коэффициенты для консервативной и оптимистичной границ заданы в `src/config.ts`. Если
`2600 ≤ T_eff ≤ 7200 K`, полином считается как есть. В диапазонах `2300–2600` и `7200–7600 K`
он считается на ближайшей границе, ставится `hzExtrapolated` и бейдж «ЗО: экстраполяция». Вне
`[2300, 7600] K` или при `d_out ≤ d_in` значение `F_HZ` равно `null`.

### Штрафы и Q_data

```text
P_rocky(R) = 1 / (1 + exp(5·(R − 1.65)))
P_ecc(e)   = 1 − e²
P_star     = 0.85 при T_eff < 3900 K, иначе 1.00
```

Q_data стартует с `1.00`:

- `−0.10`, если масса или радиус получены на Уровне Б;
- `−0.05`, если эксцентриситет принят равным нулю (кроме `P < 10` сут);
- `−0.05` за каждый субиндекс, исключённый на Уровне В (только в «Адаптивном»);
- итог — не ниже `0.75`.

Бейдж: `≥ 0.95` — «Высокая», `0.85–0.95` — «Средняя», ниже — «Оценочная».

Штрафы и Q_data входят в формулу **только** в режимах «Адаптивный» и «RHI». В «Упрощённом ESI»
и «Строгом научном» они не применяются, а колонка Q_data показывает «—». При этом ползунок
минимального Q_data (75–100 %) фильтрует выдачу **во всех режимах** независимо от чекбокса.

### Четыре режима

| Режим | Формула | Особенности |
|---|---|---|
| Адаптивный | `geomean(ESI_R, ESI_ρ, ESI_v, F_HZ)` при `k ≥ 3`, затем штрафы и Q_data | при полных данных не равен RHI |
| RHI | `sqrt(ESI_interior · F_HZ)` · штрафы · Q_data | только при всех четырёх субиндексах |
| Упрощённый ESI (R, S) | `sqrt(ESI_S · ESI_R)` | без штрафов и Q_data; это не PHL-ESI |
| Строгий научный | `sqrt(ESI4 · F_HZ)` | только измеренные `R`, истинная `M`, `e`, `a` или `P`, `T_eff`, `M_*`, `L` или `R_*` |

Переключатель границ ЗО влияет на «Адаптивный», «RHI» и «Строгий научный». Ранжирование: индекс
по убыванию, при равенстве — Q_data по убыванию, затем имя. Топ-50 строится после фильтров.

### Калибровка Земли и известное расхождение

Строка «Земля (эталон)» не входит в Топ-50 и считается тем же кодом из констант: `R = 1`,
`M = 1`, `e = 0.0167`, `a = 1 а.е.`, `P = 365.25 сут`, `T_eff = 5772 K`, `L = 1 L☉`,
`M_* = 1 M☉`.

Для консервативной ЗО реализация даёт `F_HZ ≈ 0.254` и `RHI = sqrt(1 · 0.254) ≈ 0.504`.
В исходном ТЗ указан диапазон `[0.46, 0.50]` и ориентир `≈ 0.48`. Формула `F_HZ = 1 − HZD²`
оставлена без изменений: расхождение возникает из-за положения Земли у внутреннего края ЗО, а не
из-за ошибки вычислений. Оно зафиксировано в тесте `calc.test.ts` и описано в разделе
«Ограничения». Для оптимистичной ЗО `F_HZ` Земли ≈ 0.74, что попадает в ожидания ТЗ.

## 3D-визуализация

Карта Галактики использует экваториальные координаты J2000:

```text
x = r·cos(dec)·cos(ra), y = r·cos(dec)·sin(ra), z = r·sin(dec)
r = sy_dist из слияния, Земля в (0,0,0)
r′ = 900 · log10(1 + r), направление сохраняется
```

Планеты без `ra`, `dec` или `dist` на карту не попадают; их число показано отдельно. Топ-50
подсвечен изумрудным, выбранная планета — янтарным. Камера управляется OrbitControls; есть
«Обзор» и «Сбросить камеру» с плавным перелётом.

Сцена системы строится процедурно, без внешних текстур и моделей. Цвет звезды аппроксимируется
по `T_eff` через blackbody → sRGB, размер — по `R_*`; свет — PointLight. Тип планеты выбирается
по радиусу и `T_s`: ледяной, землеподобный, пустынный, лавовый, мини-нептун, ледяной или
газовый гигант. Есть вращение, дрейф облаков и синхронное вращение при `P < 10` сут или
`T_eff < 3900 K`. Показываются орбита с эксцентриситетом и кольцо ЗО. В режиме «1:1» соблюдаются
реальные пропорции, поэтому в кадре может быть только один объект; переключение сохраняет выбор
и плавно двигает камеру. Бейдж «Реконструкция по расчётной модели» показывается для Уровня Б.

Если данных недостаточно (`insufficientData` или нет `R`/`T_s`), планета рисуется тёмно-серой
сферой без рельефа и атмосферы, вокруг добавляется облако пыли, а над объектом появляется «?» и
подпись «недостаточно данных для отрисовки»; при наведении перечисляются недостающие поля.
Геометрии и материалы освобождаются при смене планеты и размонтировании.

## Снимки

Снимки — аварийный слой, а не источник данных при обычной работе. Их создаёт человек перед
демонстрацией; приложение не скачивает их на этапе сборки.

```bash
# из корня: LIVE, при ошибке — локальный резерв
node scripts/make-snapshots.mjs

# только из локальных резервов data/backups
node scripts/make-snapshots.mjs --backups

# только один источник / свой каталог
node scripts/make-snapshots.mjs --only=nasa,gaia
node scripts/make-snapshots.mjs --out=public/data/snapshots
```

Генератор `frontend/scripts/make-snapshots.mjs` поднимает Vite в SSR-режиме и загружает
`frontend/scripts/snapshot-runner.ts`, поэтому используются **те же** модули `src/lib/sources`,
парсер, SCHEMA GUARD и прямой транспорт, что и в приложении. Для каждого источника пишется файл
`<source>.json`:

```json
{
  "meta": {
    "source": "nasa",
    "fetchedAt": "2026-11-14T00:00:00.000Z",
    "recordCount": 6470,
    "endpoint": "https://exoplanetarchive.ipac.caltech.edu/TAP/sync",
    "schemaVersion": 1,
    "missingColumns": [],
    "origin": "backup"
  },
  "rows": []
}
```

`origin` показывает, откуда взялся снимок: `live` или `backup`. Валидация при чтении
(`parseSnapshot`) проверяет `meta`, `source`, `recordCount` и массив `rows`; лишние поля `meta`
сохраняются. Снимки, созданные 14.11.2026 из локальных резервов: NASA — 6 470, Exo-MerCat —
17 617, Exoplanet.eu — 8 477, Gaia — 2 000, SIMBAD — 5 000 записей. Это меньше LIVE-выгрузок
Gaia/SIMBAD, потому что `scripts/fetch-sources.ps1` ограничивает размер резервов; после LIVE-
загрузки приложение использует полные ответы.

Сырые выгрузки `data/` в репозиторий не коммитятся. Снимки `frontend/public/data/snapshots/`
коммитятся, чтобы они попали в деплой Vercel и работали как аварийный слой.

## Хранилище Supabase (Postgres)

Каталоги экзопланет можно хранить в Supabase и отдавать приложению оттуда: это снимает
зависимость от доступности TAP-источников и ускоряет старт (одна-две выгрузки вместо пяти
сетевых запросов).

### 1. Схема базы

Выполните `supabase/schema.sql` в Supabase Dashboard → SQL Editor (или через `psql`):

| Таблица | Содержимое |
|---|---|
| `catalog_snapshots` | метаданные выгрузки: источник, дата, число записей, endpoint, колонки |
| `catalog_rows` | строки выгрузки в исходном виде (`jsonb`), порядок — в `ord` |

Обе таблицы закрыты RLS без политик: читать и писать может только `service_role`.
Публичный `anon`-ключ к ним доступа не имеет.

### 2. Куда вписать токен

Файл `frontend/.env.local` (создан, в репозиторий не попадает):

```dotenv
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_SERVICE_ROLE_KEY=<ключ с полным доступом>
SUPABASE_CATALOG_WRITE_KEY=<любой длинный секрет, если нужна запись из браузера>
```

- `SUPABASE_URL` — URL проекта из Dashboard → Project Settings → API.
- `SUPABASE_SERVICE_ROLE_KEY` — ключ доступа к базе. Поддерживаются два вида:
  - `sb_secret_…` или legacy `service_role` JWT — ключ проекта (Dashboard → API Keys);
  - `sbp_…` — Personal Access Token (Dashboard → Account → Access Tokens). Тогда сервер
    сам возбирает ключ проекта через management API (`GET /v1/projects/<ref>/api-keys`).
    Новый secret-ключ management API отдаёт замаскированным, поэтому используется
    legacy `service_role` JWT.

  Значение используется **только на сервере**: в Edge-функции `/api/catalog` и в скриптах
  загрузки. В бандл фронтенда оно не попадает и в браузер не отдаётся. Ключ проекта
  кэшируется в памяти процесса на 10 минут.
- `SUPABASE_CATALOG_WRITE_KEY` — дополнительный секрет для записи из браузера (заголовок
  `x-catalog-key`). Не задан — запись через API закрыта, чтение работает.

Шаблон с комментариями — `frontend/.env.example`. Для Vercel те же переменные задаются
в настройках проекта (Environment Variables).

### 3. Загрузка каталогов в базу

```bash
cd frontend
npm run snapshots -- --backups   # или без флага — LIVE-выгрузки
npm run upload:catalog            # выгрузка снимков в Postgres
npm run upload:catalog -- --only=nasa,gaia
npm run supabase:schema           # применить supabase/schema.sql (нужен PAT)
```

Скрипт `frontend/scripts/upload-catalog.mjs` читает `public/data/snapshots/*.json` и кладёт их
в таблицы через PostgREST, используя ключ доступа к базе. Хранятся последние три версии
выгрузки на источник, старые удаляются каскадом.

В самом приложении панель «Источники» показывает состояние подключения и позволяет выгрузить
текущий резерв источника в базу по кнопке «В Supabase» (нужен ключ записи). Галочка
«Брать каталоги из Postgres как из основного источника» переключает приложение на режим,
в котором каталоги читаются из базы без запросов к TAP.

### 4. Маршруты

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/catalog?health=1` | проверка подключения и доступности таблиц |
| `GET` | `/api/catalog?sources=nasa,gaia` | последние выгрузки источников (метаданные + строки) |
| `POST` | `/api/catalog` | запись выгрузки; заголовок `x-catalog-key` |

Маршрут обслуживает Edge-функция `frontend/api/catalog.ts` (секреты — в переменных окружения
Vercel) и dev-плагин `frontend/vite.dev-proxy.ts` (секреты — из `frontend/.env.local`).

## Деплой на Vercel

Проект рассчитан на статический Vite-билд и одну Edge-функцию.

1. Импортируйте репозиторий в Vercel.
2. **Root Directory** — `frontend` (не корень монорепозитория).
3. Framework Preset — Vite; Build Command — `npm run build`; Output Directory — `dist`;
   Install Command — `npm ci`. Node.js 18+.
4. Переменные окружения не нужны, кроме случая с Supabase: тогда задайте `SUPABASE_URL` и
   `SUPABASE_SERVICE_ROLE_KEY` (см. «Хранилище Supabase»).
5. Убедитесь, что `frontend/api/proxy.ts` попал в деплой: Vercel создаст Edge-функцию
   `/api/proxy` с allowlist хостов.
6. Снимки должны быть в репозитории (каталог `frontend/public/data/snapshots/`), иначе при
   недоступности API и пустом IndexedDB приложение корректно пропустит источники, но не покажет
   аварийные данные.

Через CLI:

```bash
cd frontend
npx vercel --prod
```

Для временного демо без входа в аккаунт:

```bash
cd frontend
npx vercel deploy --temporary --yes
```

Важное ограничение Vercel: анонимный temporary-деплой **не принимает Edge runtime**
(`The Edge runtime is deprecated and cannot be used for anonymous deployments`). Поэтому для
одного демонстрационного деплоя 14.11.2026 был вручную собран prebuilt-выгрузка
(`.vercel/output`) со статикой Vite и тем же обработчиком `api/proxy-handler.ts`, обёрнутым в
Node.js-функцию. Это обход только для анонимного демо; файлы `.vercel/` в репозиторий не входят.
Штатная конфигурация для авторизованного аккаунта остаётся прежней: `frontend/api/proxy.ts` как
Edge-функция. Либо после `vercel login` выполните `npx vercel --prod` из `frontend/`.

Проверка прокси после деплоя:

```bash
curl -i "https://<домен>/api/proxy?u=https%3A%2F%2Fexoplanetarchive.ipac.caltech.edu%2FTAP%2Fsync%3Fquery%3DSELECT%2B1%26format%3Djson"
```

Ожидаемы ответы: `400` без `u`, `403` для чужого хоста, `200` для разрешённого.

## Тесты и проверка

```bash
cd frontend
npm run typecheck
npm run test
npm run build
```

На 14.11.2026: **10 файлов, 113 тестов, все проходят**; `tsc --noEmit` и production-сборка
завершаются успешно. Тестовые данные находятся только в `*.test.ts` и помечены `// TEST FIXTURE`.

Покрыто обязательными тестами:

- Земля: `ESI_interior = 1`, `S ≈ 1`, `T_eq ≈ 255`, `F_HZ` в ожидаемых диапазонах, RHI ≈ 0.504;
- TRAPPIST-1 e: `hzExtrapolated = true`, `ESI_interior` и `F_HZ` в заданных диапазонах;
- третий закон Кеплера: `a = 1`, `M_* = 1` → `P = 365.25`;
- Чен—Киппинг, включая `R = 13 → M = null` и `M = 200 → R = null`;
- `k < 3`: `insufficientData = true`, индекс `0.00`, исключение из адаптивного Топ-50;
- `normName`: разные написания имени дают один ключ;
- дедупликация: разные буквы и периоды не склеиваются, неоднозначный S3 даёт предупреждение;
- консенсус: выбор ближайшего к медиане, `conflict` при двух кандидатах;
- парсер: JSON-массив, `{metadata, data}`, CSV-fallback, `UnknownFormat`;
- транспорт: HTTP через прокси, повтор после `TypeError`, `429` с `Retry-After`;
- SCHEMA GUARD: пересечение желаемых и реальных колонок, отсутствующие — в диагностику;
- числовая устойчивость: нет `NaN`/`Infinity` в вычисленных значениях и индексах.

Проверено вживую в Chromium 14.11.2026 на dev-сервере: пайплайн завершается, пять стартовых
источников получают LIVE, Exo.MAST остаётся ленивым; переключение режимов, фильтры (включая
сброс и пустую выдачу), карта, сцена, карточка, уведомления и URL-состояние работают. Экспорт
CSV реализован на клиенте, но в ходе этого QA отдельно не проверялся. Ожидаемые CORS-ошибки
прямых запросов видны в консоли, после них транспорт успешно переходит на `/api/proxy`; это не
ошибка приложения.

Там же проверена temporary-выгрузка Vercel (Node-обёртка, см. «Деплой»): приложение
загружается, все пять стартовых источников получают LIVE через `/api/proxy`, встроенные снимки
отдаются с домена, Топ-50 строится, карта и сцена рендерятся, карточка и ленивый Exo.MAST
работают. Диагностика схем совпадает с dev-сервером.

## Принятые решения

- **Vite SPA вместо Next.js.** Требование — статический билд и `api/proxy.ts` как Vercel Edge
  Function; Vite + React точно соответствует структуре и не добавляет SSR, который вне scope.
- **Dev-прокси реализован Vite-плагином.** `vite.dev-proxy.ts` вызывает тот же
  `api/proxy-handler.ts`, что и продакшн; `vercel dev` не обязателен.
- **Снимки коммитятся.** Исходное ТЗ говорит, что снимки создаёт человек перед демо; для
  воспроизводимого деплоя Vercel они должны быть в репозитории. Сырые `data/` по-прежнему
  исключены через `/data/` в `.gitignore`.
- **Q_data и штрафы только в «Адаптивном» и «RHI».** В «Упрощённом ESI» и «Строгом научном»
  они не входят в формулу; колонка Q_data показывает «—». Порог минимального Q_data фильтрует
  все режимы.
- **`k < 3` в «Адаптивном».** Индекс `0.00`, но запись не участвует в ранжировании и Топ-50;
  в «RHI» она не ранжируется (`null`). Это осознанное ужесточение, чтобы «0.00» не занимал
  место в таблице.
- **`pl_eqt` не используется в расчёте.** `T_eq` всегда считается из потока, `T_s = T_eq + 33`;
  каталожное `pl_eqt` показывается только справочно.
- **Gaia/SIMBAD без идентификаторов.** Статус `skipped` («Пропущен — нет идентификаторов») не
  считается ошибкой и не вызывает баннер.
- **RHI Земли ≈ 0.504.** Формула не подгонялась под `[0.46, 0.50]` из ТЗ; расхождение
  зафиксировано тестом и описано в README.
- **Exo.MAST только лениво.** Никаких запросов при старте; результаты не входят в стартовые
  счётчики и не имеют встроенного снимка.
- **Резервы IDB.** Показываются сразу при старте, затем заменяются LIVE-данными; хранятся до
  пяти версий, запись в одной транзакции, защита от ответа меньше 50 % предыдущего объёма.
- **Калибровочная Земля** считается тем же решателем и кодом ранжирования, но всегда вне Топ-50.

## Ограничения

- `pscomppars` — композит из разных публикаций; согласованность параметров не гарантируется.
- Масса `M·sin(i)` — нижняя граница; в интерфейсе помечается явно. Истинная масса имеет
  приоритет при слиянии.
- Полином Коппарапу экстраполируется только в узких диапазонах `2300–2600` и `7200–7600 K`;
  вне их `F_HZ = null`.
- `F_HZ = 1 − HZD²` даёт Земле `F_HZ ≈ 0.254` и RHI ≈ 0.504, хотя в ТЗ ориентир ≈ 0.48.
  Формула оставлена как есть; это свойство модели, а не ошибка.
- Отсутствующие данные не заменяются нулями; из-за этого часть планет не ранжируется или не
  попадает на карту. Счётчики показывают, сколько записей исключено.
- Снимки могут быть устаревшими и содержат меньше строк Gaia/SIMBAD, чем LIVE; дата и уровень
  всегда видны.
- Exo.MAST может быть недоступен или не иметь спектра для конкретной планеты; ошибка
  показывается в карточке, прежние данные сохраняются.
- 3D-карта использует только расстояние и направление, без собственных движений и полной
  орбитальной динамики. Сцена — реконструкция по расчётной модели, а не изображение.
- В режиме «1:1» реальные пропорции делают невозможным одновременный показ звезды и планеты.
- Приложение не выполняет асинхронные TAP-задачи и не строит собственный каталог; вся тяжёлая
  работа — в браузере.
- Нет авторизации, серверной БД и SSR; единственный серверный код — Edge-прокси.
- Данные принадлежат источникам; при публикации результата нужны ссылки на NASA Exoplanet
  Archive, Exo-MerCat, Exoplanet.eu, Gaia DR3, SIMBAD и Exo.MAST.

## Что не проверено вживую

- Авторизованный продакшн-деплой Vercel с **Edge**-функцией `frontend/api/proxy.ts`: на машине
  сборки не было `vercel login`, а анонимный temporary-деплой Edge запрещает. Временная
  выгрузка проверена с Node-обёрткой того же обработчика (см. «Деплой»); штатная Edge-конфигурация
  готова, но на реальном домене ещё не запускалась.
- `vercel dev`: локально использовался Vite-плагин с тем же обработчиком прокси.
- График реального спектра Exo.MAST: проверены identifiers/properties/filelist и обработка
  ошибок, но планета с доступным файлом спектра в ходе QA не попалась.
- Safari, Firefox, мобильные браузеры и экранные читалки.
- Полное отключение сети после прогрева IDB, троттлинг и очень медленные ответы всех шести
  источников одновременно.
- Долгосрочный rollover пяти версий IDB и поведение при переполнении квоты.
- Нагрузка на каталогах существенно больше 17 750 сущностей.
